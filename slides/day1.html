What can make a step slow

Every step is limited by compute, memory capacity or memory bandwidth

Compute

Floating-point operations per second the processor can do. A large matrix product runs into this roof.

Capacity

Bytes that fit at all. Too many and the run fails, or spills to slower memory. Day 2 is about this one.

Bandwidth

Bytes per second between memory and the cores. Elementwise layers and decoding one token at a time run into this roof.

What goes wrong. Optimising the limit that does not bind. Fewer FLOPs do not help a step that waits for memory.

Ask the room for an example of each from their own work: an out-of-memory error is capacity; a GPU at 20% utilisation is often bandwidth or input. The rest of today puts numbers on the laptop's two rates, compute and bandwidth.

Arithmetic intensity = FLOPs divided by bytes moved. It is a property of the layer, not of the machine.

Work layer A on the board before showing the row: one multiply and one add per weight per row of the batch. Then ask the room to do B themselves. These are the two layers of Lab 1.1, and the estimates are AI-off.

The roofline idea

Attainable speed is the lower of two roofs

attainable = min(peak, intensity x bandwidth)

Below the ridge point a layer waits for memory; above it, for arithmetic.

Ridge point = peak / bandwidth

The intensity at which the two roofs meet.

  • A floor on time, never a promise: real layers sit under their roof.
  • It tells you which roof to push: fewer bytes or fewer FLOPs.
  • Batching raises intensity: the weights are read once for more rows.

The model is from Williams, Waterman and Patterson's 2008 Berkeley report. Draw it on the board with log axes: a sloped line (bandwidth) that meets a flat line (peak). Sources: Roofline technical report, EECS-2008-134.

Caches and data movement

Data reused close to the cores is cheap; data fetched from main memory is not

Registersa few hundred bytes per core
→
L1 and L2 cachestens of kilobytes to a few megabytes
→
Last-level cachemegabytes, shared
→
Main memorygigabytes, the bandwidth you measured
Why the matrix product is fast. It works on tiles that stay in cache and reuses each number many times. The 256 MB copy cannot: it reads everything once.

Keep the sizes as orders of magnitude; exact figures depend on the processor generation and change every year. The lesson that lasts: an operation's speed depends on how often it reuses what it loaded. Fusion (Day 2) and batching (Day 3) are both ways to reuse data.

CPUs, GPUs and neural accelerators

Each processor trades generality for throughput on dense arithmetic

CPU

Few strong cores with wide vector units. Good at branches, small batches and everything around the model.

GPU

Thousands of simple lanes and very high memory bandwidth. Needs large, regular work to stay busy.

Neural accelerator

Fixed-function units for matrix products in low precision, on many new laptops and phones. Needs a runtime that supports it.

Same roofline, different numbers. Each has its own peak and bandwidth, so the same layer can bind differently on each.

Nama's laptops are processor-only, which is why the course measures on CPUs. The free Colab GPU is optional; on Day 2 participants who try it will see mixed precision behave very differently. Hardware figures go stale fast: keep them off slides and measure.

Timers

Time with a monotonic clock, around the call, many times

ms = []
for _ in range(100):
    t0 = time.perf_counter()
    with torch.no_grad():
        model(leaf)
    ms.append((time.perf_counter() - t0) * 1000)
  • perf_counter never jumps; time.time follows the wall clock, which can be adjusted.
  • On a GPU, call torch.cuda.synchronize() before reading the clock: the work is asynchronous.
  • One timing is an anecdote. A hundred are a distribution.

Demonstrate in a notebook: time one call five times and show five different numbers. Then ask what Mutaib meant by "it takes 5 ms": which of these numbers?

Timers and profilers

A timer says how long; a profiler says what ran

Timers

Cheap, honest about wall time, blind to what happened inside. Put them around phases you name.

Profilers

Record every operator or sample every call stack. Show where time goes inside a phase, with some overhead of their own.

Use both. Timers to find the slow phase, a profiler to find why it is slow, timers again to prove the fix.

Session 3 uses the framework's profiler on a training step; py-spy and Scalene are Python-level profilers that see the data loader too. memray is a memory profiler for Linux and macOS only.

A training step

A training step has four phases, and any of them can be the slow one

1 · Loadread, decode, augment, batch
→
2 · Forwardcompute the loss
→
3 · Backwardcompute the gradients
→
4 · Optimiserupdate the weights
What goes wrong. Buying a faster processor for a step that waits for its data.

Backward usually costs about twice the forward pass. The optimiser is small for a small model. Loading is the one people forget: it is not in the model code at all.

The supplied slow script

Lina's loader decodes a 224-pixel PNG and rotates it at full size, for every leaf, every epoch

img = Image.open(self.folder / name).convert("RGB")   # decode a PNG
img = img.rotate(angle, resample=Image.BILINEAR)       # augment at 224 px
img = img.resize((64, 64), Image.BILINEAR)             # then shrink
x = torch.tensor(np.array(img), dtype=torch.float32)   # one leaf at a time
# ... in the main process: num_workers=0

Do not point out the problems yet: ask the room to predict which phase will be largest and write the guess down. Lab 1.3 checks the guess.

Timers around phases

Four timers split the step; on a GPU, synchronise before each reading

t0 = time.perf_counter(); x, y = next(batches)
t1 = time.perf_counter(); loss = F.cross_entropy(model(x), y)
t2 = time.perf_counter(); loss.backward()
t3 = time.perf_counter(); opt.step(); opt.zero_grad()
t4 = time.perf_counter()
# GPU: torch.cuda.synchronize() before each perf_counter()

Skip the first two steps: they pay for start-up. The lab's run() does this. On a GPU without synchronisation the backward phase looks instantaneous and the next phase pays for it.

The ceiling of a fix

Removing one phase can never beat the sum of the others

2.9 x
the most Lina's step can gain if loading cost nothing (Lab 1.3)
  • Speed-up limit = 1 / (1 - share of the phase you fix).
  • Compute this before you start: it says whether the fix is worth a day.
  • After the fix, the next phase is the bottleneck: measure again.

This is Amdahl's law applied to one step. It also explains why a faster GPU did nothing for Lina: the GPU would only shrink forward and backward.

Input-bound against compute-bound

A step is input-bound when the model waits for its next batch

Input-bound

Loading is the largest phase. A faster model changes nothing. Fix the pipeline.

Compute-bound

Forward and backward dominate. The pipeline is good enough. Days 2 and 3 work here.

Signs. A GPU at low utilisation; one core at 100% while others idle; step time that does not change with model size.

Ask the room how they would tell the two apart without a profiler: replace the loader with random tensors of the right shape. If the step gets much faster, it was input-bound.

JPEG is lossy: the two decoded leaves differ by 2.5 of 255 per pixel on average. Whether that matters is a quality question, measured, not seen.

Most of the gain is the size: the model needs 64 pixels and the export ships 224. The cheapest pixel is the one never stored. Formats for training at scale (WebDataset shards, arrays in one file) follow the same logic: decode once, read bytes.

Parallel loading and prefetching

Workers prepare the next batches while the model trains on this one

DataLoader(ds, batch_size=64, shuffle=True,
           num_workers=4,
           persistent_workers=True,
           prefetch_factor=2)
  • Workers hide loading behind compute; they do not make it cheaper.
  • They take cores the training step also wants.
  • On Windows and macOS each worker is a fresh Python process: the first batch is slow.

The dataset class must be importable from a module for workers on Windows and macOS (spawned processes import it); that is why the loaders live in nama.py. In a script, put the training under if __name__ == "__main__".

Caching preprocessed data

Decode once, store the 64-pixel bytes, read bytes every epoch

50 MB
for 4,096 leaves as one uint8 array, built once in 88 s (Lab 1.4)
  • The cache is right when preprocessing is the same every epoch.
  • It is wrong when augmentation must differ each epoch at full size, or when the data changes faster than the cache.
What it changed besides speed. Lina rotated by any angle; the cache rotates by multiples of 90 degrees. A speed-up that changes what the model learns is checked for quality.

This is the course's recurring trap: every optimisation changes something else. Day 4 is the formal check. Ask the room which other change today might affect quality: the JPEG format.
