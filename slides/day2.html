Where memory goes

01
What a training step holds

Training memory has four parts, and only one grows with the batch

Weights

4 bytes per parameter in float32.

Gradients

One per weight: another 4 bytes.

Optimiser state

AdamW keeps two numbers per weight: 8 bytes.

Activations

What the forward pass keeps for the backward pass: grows with batch and image size.

Rule of thumb. 16 bytes per parameter before any activation, for float32 and AdamW.

Work the rule on a 1-billion-parameter model: 16 GB before activations. For Waraqa (about 290,000 parameters) it is under 5 MB. Ask: so where does Waraqa's memory go? The answer is the next slide.

Explain every difference

Each gap between estimate and measurement has a name

Estimate < saved

Pooling indices (8-byte integers) and the input batch were not counted.

Saved < peak

Gradients of activations and convolution work buffers are alive during the backward pass.

Small batches

Fixed costs dominate: weights, optimiser state, the allocator's own reserve.

LO3 evidence. The estimate table next to the measured peaks, with each difference explained in a line.

The goal is not a perfect estimate; it is an estimate whose errors you can name. A gap you cannot explain is a bug or a leak waiting to be found.

02
Number formats (recap of AE-202)

Sixteen bits buy half the bytes and give up range or precision

FormatBitsExponent / fractionGives up
float32328 / 23nothing: the reference
float16165 / 10range: small gradients underflow to zero
bfloat16168 / 7precision: the range of float32, fewer digits
int88integer with a scaleboth, recovered by calibration (Day 3)

A one-slide recap: AE-202 introduced number formats. The point for today: fewer bytes per number halve the memory traffic, and speed only comes if the hardware computes in that format.

Mixed precision

Autocast runs the heavy operations in 16 bits and keeps the rest in 32

with torch.autocast("cpu", dtype=torch.bfloat16):
    out = model(x)                  # convolutions in bfloat16
    loss = F.cross_entropy(out.float(), y)
loss.backward()                      # gradients flow back
opt.step()                           # float32 master weights
  • Mixed: weights and optimiser stay in float32; small updates would vanish in 16 bits.
  • On a CPU, autocast defaults to bfloat16; on a GPU to float16.
  • float16 needs a gradient scaler to keep small gradients from underflowing.

Sources: PyTorch 2.15 documentation, torch.amp: the default autocast type is bfloat16 on CPU and float16 on CUDA. The next two slides show what the gradient scaler is for and how to read the signs that a run needs one.

Measured: Hasad, one backward pass on 32 questions it already answers well

float16 lost 2.9% of Hasad's gradients without a single error

Layer groupEntriesZero in float16 only

  • Loss 0.000415 in both runs, no infinity or NaN: not overflow.
  • The same batch in float32 gives every one of these entries a nonzero gradient: not the learning rate.
  • Gradients that are zero only in float16 fell below its smallest number, about 6e-8: underflow.

How the numbers were made: labs/_tools/fp16_underflow.py runs one backward pass of the finished Hasad model on 32 farmer questions (loss on the answer only), once in float32 and once with float16 autocast on the same batch, and counts the entries that are nonzero in float32 and exactly zero in float16. The whole gradient differs from float32 by 12.23%. The loss is tiny because Hasad already answers these questions, which is exactly when gradients are small: late in training and on fine-tuning. Embeddings suffer most because most of their rows receive tiny gradients. Ask the room to read the table before the bullets appear: which column rules out overflow, which rules out the learning rate? Lab 2.2's stretch does the same on Waraqa.

The fix: scale the loss, unscale the gradients

A scale of 65,536 brings the lost gradients back; too large a scale overflows

Loss scaleLostInf or NaNError vs float32
12.90%012.23%

scaler = torch.amp.GradScaler("cuda")
with torch.autocast("cuda", dtype=torch.float16):
    loss = loss_fn(model(x), y)
scaler.scale(loss).backward()   # loss x scale
scaler.unscale_(opt)            # before clipping
clip_grad_norm_(model.parameters(), 1.0)
scaler.step(opt)                # skipped on inf or NaN
scaler.update()                 # adjust the scale

PyTorch's scaler starts at 65,536, halves the scale and skips the step when it finds inf or NaN, and doubles it after 2,000 clean steps.

Same batch and script as the previous slide, now with the loss multiplied by the scale before backward and the gradients divided by it afterwards. The 0.30% error that remains is float16's rounding, not lost entries. The scales are powers of two (2 to the 8, 16, 24 and 32), so multiplying and dividing is exact. At 4.3 billion nearly every gradient overflows: that is why the scaler backs off. Source: PyTorch 2.15, torch.amp.GradScaler (defaults init_scale 65536, growth_factor 2, backoff_factor 0.5, growth_interval 2000) and the AMP examples page (step skipped when gradients hold inf or NaN; unscale_ before clipping). bfloat16 keeps float32's range, so it needs no scaler: that is why Lab 2.2's main runs use none.

Why did bfloat16 not help here?

On a laptop whose processor reports AVX2 only, bfloat16 autocast made Waraqa's training step slower with the same accuracy. What is the best explanation?

The model is too small to benefit from any optimisation
bfloat16 lost precision, so the step had to do more work
The processor has no native bfloat16 arithmetic, so each operation pays for conversions
The optimiser now runs in bfloat16 and needs more steps
Why. Without native support the lower precision is emulated: numbers are converted to float32 to compute and back, which adds work instead of saving it.

1,174 MB

  • The learning rate and schedule were tuned for 256: a smaller batch changes training.
  • Two ways to keep 256: accumulate, or recompute.

Gradient accumulation

Four micro-batches of 64, one optimiser step

for xm, ym in zip(x.chunk(4), y.chunk(4)):
    loss = F.cross_entropy(model(xm), ym) / 4
    loss.backward()        # gradients add up in .grad
opt.step()
opt.zero_grad()
  • Divide each loss by the number of micro-batches: the sum is the mean over 256.
  • Activations of one micro-batch at a time: about a quarter of the memory.
  • Costs time: four smaller calls do less work in parallel.

A common bug: forgetting the division, which makes the gradient four times too large. With plain SGD every step is then four times too long; AdamW divides by the gradient's running size, so it hides most of the error, which is why the bug survives unnoticed until someone changes the optimiser or adds gradient clipping. Another: calling zero_grad inside the loop.

Checked in Lab 2.3

Accumulation equals a large batch only for layers that treat each example alone

Batch norm modeLargest relative gradient difference
Evaluation (stored statistics)3.8e-05
Training (statistics per batch)1.2

With batch norm, each micro-batch is normalised by its own statistics. It usually trains fine; it is not the same computation.

Evaluation mode proves the arithmetic is right (rounding only); training mode shows the honest difference. Layer norm and group norm do not have this issue: they normalise each example on its own.

Activation checkpointing

Keep a few activations, recompute the rest during the backward pass

from torch.utils.checkpoint import checkpoint_sequential
feats = checkpoint_sequential(model.features, 4, x,
                              use_reentrant=False)
logits = model.head(feats.mean(dim=(2, 3)))
  • Only the boundaries of 4 segments are kept; each segment's inside is recomputed when its gradient is needed.
  • Trades about one extra forward pass for memory.
  • The idea is from Chen et al., 2016: memory that grows more slowly than depth.

Sources: Chen, Xu, Zhang and Guestrin, Training deep nets with sublinear memory cost (arXiv 1604.06174); PyTorch 2.15 torch.utils.checkpoint. use_reentrant=False is the recommended variant in current PyTorch.

What does activation checkpointing reduce?

A language model of 2 B parameters does not fit for training on a 24 GB GPU even at batch 1. Will activation checkpointing make it fit?

Yes: checkpointing reduces all training memory

04
Operator fusion

Separate operations read and write the whole activation each time

Convolutionwrites z
→
Batch normreads z, writes y
→
ReLUreads y, writes y
Fused. One kernel computes the convolution, the affine map and the ReLU while the data is still in cache: one write instead of three.

Batch norm and ReLU are elementwise, so memory-bound (Lab 1.1's layer B): fusing them into the convolution removes their memory traffic.

One fusion by hand

At inference, batch norm folds into the convolution's weights

s = bn.weight / torch.sqrt(bn.running_var + bn.eps)
W_new = conv.weight * s.reshape(-1, 1, 1, 1)
b_new = bn.bias - bn.running_mean * s
  • At inference batch norm is a fixed affine map per channel; a convolution is linear: the two combine.
  • Not during training: the statistics change every batch.
  • Outputs agree to rounding: largest logit difference 5.7e-06 in Lab 2.4.

AI-off for the formula. Derive it on the board: y = gamma (Wx - mean) / sqrt(var + eps) + beta. Runtimes do this automatically (Day 4's ONNX Runtime does); doing it once by hand shows what "fusion" means.

Compilation

A compiler captures the graph, fuses operations and generates code once

  • torch.compile(model): capture on the first call, then reuse the generated code.
  • Its default backend generates C++ for processors: it needs a C++ compiler.
  • Colab, Linux and macOS usually have one; the course's Windows laptop did not.

Two numbers, always

The first-call cost (capture and code generation) and the steady-state speed per call.

Sources: PyTorch 2.15 torch.compile documentation. On the build laptop, torch.compile failed with "cl is not found": the Windows C++ compiler was not installed. The lab falls back to the aot_eager backend, which captures the graph without generating code, and says so. Run the lab in Colab to see the inductor backend.

Checkpoint

Is compilation worth it here?

Compiling Waraqa costs 20 s on the first call and saves 2 ms per batch. The field app starts, classifies about 50 leaves, and closes. Should it compile at start-up?

Yes: 2 ms per batch is a 20% gain
No: 50 leaves save well under a second, and the agent waits 20 s at every start
No: compilation lowers accuracy
Yes: the gain grows the longer the laptop runs
Why. The first call is repaid only after about 10,000 batches in one process; a short-lived app never gets there. A long-running service, or a cached compiled artefact, does.

Answer: B. This is why Day 4 exports to a runtime file: the optimisation is done once, ahead of time, and every start is fast.
